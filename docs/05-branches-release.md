# 分支与发布

## 版本管理

`hkrime` 的当前开发分支为 `dev`，`main` 是 without-CMake 基线；两条线包名和内容不同，
不要直接互相合并。先核对 `git branch -av`、`git status` 与目标提交再操作。
JNI 工程与其 librime 源码为独立仓库，跨仓库变更要分别记录提交，并同步可重放补丁。
依赖源码不由 App 仓库跟踪，不能只提交 App 的 `.so` 就声称变更已完整保存。

提交信息使用中文和范围前缀，如 `fix(preedit): …`、`feat(12鍵/面板): …`、`perf(librime): …`。
行为或协议变更同步相应文档；面板语义变更先写明规则并向用户确认再实现。

## 发布流程

1. 确定 App、JNI、librime 与插件的实际版本和工作树状态；完成相关测试。
2. 验证 JNI 符号、实际 ELF LOAD 对齐与资产引用；当前库对齐见 [02](02-jni-so.md)。
3. 用发布密钥构建 Release；使用 SDK build-tools 的 `apksigner verify --verbose --print-certs <apk>`
   核对签名，用 `zipalign -c -P 16 4 <apk>` 检查 ZIP 对齐。
4. 在目标 arm64 设备覆盖安装，重设 appops 与输入法，完成 12 键/全字母方案验收。
5. 对交付 APK 记录文件名、字节数、SHA-256、证书指纹与对应源码版本；声明未通过的兼容项。

APK hash 只标识该次产物。关于页含本次构建时间，因此不能承诺不同构建产生相同 hash。
更换证书会影响覆盖安装；不得通过清空用户数据绕过发布问题。

## 密钥与数据

密钥、口令、真实语料、userdb 和日志不提交进 Git。签名配置见 [03](03-build.md)。
默认存储在公共目录，发布测试前保护用户词库与自定义文件；测试完成恢复所使用的隔离配置。
任何历史上公开过的凭据均不能用于当前发布，不在文档中复述其内容。
